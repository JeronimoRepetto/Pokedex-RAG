# 0027 — 2026-08-06 — 5.2: retrieval metrics as pure functions

## What was done

- **`evals/metrics.py`:** `recall_at_k`, `reciprocal_rank`, `top_1_hit`, `ndcg_at_k` —
  all pure `(retrieved: list[int], relevant: list[int], ...) -> float`, no I/O. Binary
  relevance only (the golden schema has no graded relevance). `top_1_hit` is a binary
  hit/miss (Hit@1), deliberately distinct from `recall_at_k(..., k=1)` which gives
  partial credit when multiple relevant ids exist — both are useful and answer
  different questions, so both exist rather than picking one.
- **`evals/scoring.py`:** glue between a `GoldenCase` + raw retrieved ids and the
  metrics above (`score_text_retrieval`, `summarize` for suite-level means via
  `statistics.mean`).
- Wired into `evals run`: prints per-case scores and suite averages, replacing the
  raw-hits-only output from 5.1.

## Why

Keeping metrics as pure functions (no API client, no case-loading) means they're
exhaustively testable without any mocking — every edge case (empty inputs, ties,
k larger than the list, k smaller than the relevant set) is a plain assertion.

## How it was tested

37 new metric tests (edge cases: empty retrieved/relevant, duplicate ids, k boundary
conditions, multi-relevant partial credit, nDCG rank-sensitivity) + 5 scoring tests +
1 CLI test updated for the new output format. Full evals suite: 42 passed. Fixed one
test with a wrong premise while writing these (binary-relevance nDCG doesn't
distinguish order between two equally-relevant top-k slots — caught immediately by
running it, not shipped).

## Cost

$0 — pure functions, no network.
