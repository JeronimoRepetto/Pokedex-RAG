# 0030 — 2026-08-06 — 5.5: LLM judge + conditional reformulate/abstain

## What was done

- **`api/rag/judge.py`:** `LLMJudge` — a groundedness/hallucination verdict from an
  `LLMGateway`, structured via `response_mime_type=application/json` (never free-text
  parsing). `FakeJudge` mirrors `FakeLLM`'s scripted-then-default pattern for tests.
  A judge failure (provider error, unparseable JSON) **fails open** — assumed
  grounded, with a warning — a broken judge must never take down `/chat`; it's a
  quality gate, not a correctness gate.
- **Graph:** `validate → judge → (conditional: end | reformulate → generate | abstain
  → end)`. `reformulate` increments `attempt` and loops back to `generate`, which now
  appends the judge's rejection reasoning into the retry prompt — a real second
  attempt, not a blind identical retry. `abstain` sets
  `status=insufficient_evidence`, `answer=None`, clears citations, and records how
  many attempts were rejected. Bounded by `RagDeps.max_attempts` (default 2): attempt
  < max → reformulate, else → abstain. No unbounded loop possible.
- **Enforced in config, not convention:** `JUDGE_PROVIDER` must differ from
  `LLM_PRIMARY` — checked at startup (`ValueError` if equal), so a model can never end
  up grading its own homework by misconfiguration. Empty `JUDGE_PROVIDER` disables
  judging entirely (every existing test — 64 of them — kept passing unchanged, since
  `deps.judge is None` short-circuits the whole judge/reformulate/abstain subgraph).
  Real config: `LLM_PRIMARY=vertex-gemini`, `JUDGE_PROVIDER=ai-studio-gemini` — reuses
  Phase 4.2's second provider directly, no new infra needed.

## Why

A generator grading its own output can rationalize its own mistakes; a different
model (different weights, different failure modes) is much more likely to actually
catch a hallucination the generator itself is confident about.

## How it was tested

17 new tests: 6 in `test_judge.py` (valid verdict, missing-optional-fields defaults,
non-JSON response raises, missing `grounded` key raises, `FakeJudge` scripted-then-
default, call recording), 6 graph-level routes in `test_rag_graph.py` covering **every**
route the milestone asked for — grounded-first-try (ends normally, 1 generate call),
rejected-then-reformulate-succeeds (2 calls, retry prompt carries judge feedback),
rejected-every-attempt-abstains (exactly `max_attempts` calls, never unbounded,
`status=insufficient_evidence`), a broken judge fails open instead of breaking chat,
no-judge-configured is a full no-op — plus 3 new startup fail-fast tests in
`test_app.py` (unregistered judge provider, judge == generator, judge wired
successfully with a different provider). `apps/api`: 78 passed (was 64), 8 skipped,
ruff clean.

**Live end-to-end** (real `vertex-gemini` generator + real `ai-studio-gemini` judge,
not `FakeLLM`/`FakeJudge`): asked the real running api "what type is squirtle?" —
`status=answered`, no judge-related warning, server log shows two distinct provider
calls per request ("AFC is enabled" logged twice) and `chat answered` with
`provider=vertex-gemini` — the judge ran, approved, and let the answer through on the
first try, exactly as it should for a correct answer.

## Cost

Effectively $0 for the one live smoke call (generator + judge combined, both tiny) —
cost-log updated.

## Surprises / lessons

Reusing Phase 4.2's `ai-studio-gemini` registration as the judge provider (rather than
standing up a third provider) meant zero new infrastructure for "a different model
than the generator" — the provider-portability work from Phase 4 paid for itself
again here, the same way it did for `reformulate`'s retry-with-feedback design reusing
the existing `generate` node instead of a new one.
