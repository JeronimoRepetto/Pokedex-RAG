# 0015 — 2026-08-05 — 1.8 + 1.9: API service with read endpoints

## What was done

- `apps/api` (FastAPI): app factory with fail-fast settings, `RequestIdMiddleware`
  (accepts caller's `X-Request-ID` or generates one, propagates via contextvar, returns
  it, logs an access line with duration), `/health` with per-dependency 200/503 detail,
  OpenAPI description carrying the IP disclaimer.
- Read endpoints behind a `PokemonReadRepository` Protocol (SQL implementation bound at
  startup, in-memory fake for unit tests):
  - `GET /pokemon` — pagination (max 100), filter by type and name-contains, allowlist
    regex on query params (4xx never 500);
  - `GET /pokemon/{id_or_name}` — full card (species info, types, abilities, stats,
    flavor, sprite kinds); numeric or name lookup; 404 with detail;
  - `GET /pokemon/{id_or_name}/evolution-chain` — edges with species refs and triggers.
- Multi-stage non-root Dockerfile; compose `api` service on port 8000; registered in
  Makefile/CI. CI gained the deferred `integration` job (pgvector service container,
  PRs only) covering libs/db, data-pipeline and api.
- `libs/common` fix: explicit log extras now override context defaults (the access log
  logged `request_id: null` after the contextvar reset) — regression-tested.

## How it was tested

- 13 unit tests (fake repo: pagination, filters, 422s on bad pagination/characters,
  404s, chain shape) + 5 integration tests (real migrated seeded pg).
- **Phase gate against the real ingested Gen-1 data:** 151 total; first five in dex
  order; 14 grass-types; "saur" → the bulbasaur line; Pikachu card (electric, hp 35,
  3 sprite kinds, real flavor text); squirtle→wartortle@16→blastoise@36; 404 and 422
  behave. Then the same over a real socket from the compose container: /health 200 with
  X-Request-ID, /pokemon/6 → charizard.
